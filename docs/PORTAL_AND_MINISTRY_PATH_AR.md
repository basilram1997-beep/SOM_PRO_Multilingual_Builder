# فصل البوابة المدرسية ومسار الوزارة

هذا المستند يحدد كيف يجب أن يفهم SOM PRO نفسه إذا أُضيفت له بوابة للأهالي أو الطلاب أو الرسائل، وكيف نُبقي النواة التربوية منفصلة عن أي واجهة تواصل خارجية.

## الحالة النهائية

- نظام الجدول والطاقم: مكتمل ضمن النطاق الحالي.
- بوابة الأهالي والتواصل: مكتملة ضمن النطاق الحالي بوصفها طبقة منفصلة منطقيًا.
- Multi-Tenant: مكتمل تشغيليًا ضمن النطاق الحالي مع إلزام backend schoolId والصلاحيات.

## المبدأ الأساسي

لا نخلط بين:

1. **Core Pedagogical Management**
   - إدارة الطلاب.
   - إدارة الصفوف.
   - إدارة المعلمين.
   - العلامات.
   - الحضور والغياب.
   - دفتر الصف.
   - الشهادات.
   - الأرشفة.
   - الصلاحيات.
   - Audit Log.

   هذه النواة أصبحت مكتملة عمليًا داخل المشروع الحالي، ومغطاة بالواجهة والـBackend والاختبارات الأساسية، لذلك لم تعد 1.1 مجرد أساس جزئي بل مسارًا بيداغوجيًا مكتملًا داخل المنتج.

2. **Timetable**
   - البرنامج الثابت.
   - البرنامج اليومي.
   - الاستبدالات.
   - المربين.
   - المناوبات.
   - الغرف والوقت والتعارضات.
   - إصدارات الجدول ونشره.

   هذا المسار أصبح مكتملًا عمليًا داخل المشروع الحالي، بما يشمل منطق الجدولة، وربط المربي، والاستبدالات، والمناوبات، وتعارضات الحصص، وإصدارات الجدول، لذلك لم يعد 1.2 مجرد تغطية جزئية.

3. **Parent / Student Portal**
   - عرض بيانات الطالب فقط.
   - عرض الحضور والغياب والنتائج والواجبات والإشعارات.
   - عرض الشهادات والملفات المسموح بها فقط.
   - عدم الوصول إلى أدوات التحرير الداخلية.

   هذا المسار أصبح موجودًا عمليًا داخل المنتج الحالي بوصفه بوابة مدرسية أولية مستقلة منطقيًا، عبر صفحات الطالب والإشعارات والاستدعاءات والتعهدات والشهادات والتقارير المرتبطة بها. ليس هو مجرد فكرة لاحقة؛ بل مسار تشغيل قائم ومفصول عن النواة التحريرية.

4. **Messaging**
   - رسائل النظام.
   - إشعارات ولي الأمر.
   - الاستدعاءات.
   - التعهدات.
   - سجل الإرسال والتسليم.
   - قوالب الرسائل.

## كيف نفصل البوابة عن النواة

- البوابة لا تتحدث مباشرة مع الجداول الحساسة إلا عبر API محدد.
- البوابة لا تملك صلاحيات كتابة إلا في المسارات التي نسمح بها صراحة.
- أي إرسال رسالة يجب أن يمر عبر سجل تدقيق.
- أي عرض لبيانات الأهالي أو الطلاب يجب أن يمر عبر schoolId وصلاحية واضحة.
- لا نضع منطق الرسائل داخل منطق الجدول أو العلامات.
- لا نضع منطق البوابة داخل خدمات النواة.

## ما يجب أن يبقى داخل النواة

- حساب الجداول.
- تعارضات الحصص.
- توليد البرنامج اليومي.
- توزيع الاستبدالات.
- ربط المربي والصف.
- حسابات العلامات والشهادات.
- تدقيق العمليات.
- تصدير البيانات.

## ما يجب أن يُبنى كطبقة منفصلة لاحقًا

- بوابة ولي الأمر.
- بوابة الطالب.
- صندوق الرسائل.
- إشعارات الهاتف أو البريد.
- شاشة متابعة الطلبات والرسائل.

## مسار الوزارة المتوقع

المنتج الأقرب لهذا النوع لا يُراجع فقط كبرنامج مدرسي، بل أيضًا كمنظومة تربوية قابلة للاعتماد. لذلك المسار المتوقع غالبًا يكون:

- הַקָּטָלוֹג הַחִנּוּכִי
- אישור טכנולוגי
- בדיקות אבטחת מידע
- בדיקות פרטיות
- בדיקות נגישות
- מכרז / רשימת ספקים

## متطلبات عامة قبل أي ربط حكومي

1. عزل متعدد المدارس واضح.
2. صلاحيات دقيقة على مستوى الصف/المادة/المعلم/المدير.
3. Audit Log لكل عملية حساسة.
4. تصدير وحذف بيانات قابلان للتتبع.
5. تقليل التخزين المحلي الحساس.
6. دعم RTL واللغات بشكل ثابت.
7. سياسة خصوصية وشروط استخدام واضحة.
8. اختبار نسخ احتياطي واستعادة قبل أي تسليم خارجي.

## خلاصة

SOM PRO يمكن أن يكون جاهزًا لبوابة مدرسية، لكن فقط إذا بقت:

- النواة التربوية منفصلة.
- الجدول منفصل ومكتمل كمسار مستقل.
- البوابة منفصلة.
- الرسائل منفصلة.
- العزل متعدد المدارس مفروضًا دائمًا.

هذا الفصل يجعل المراجعة أسهل، والأمن أوضح، والربط مع الوزارة أو أي جهة اعتماد لاحقة أقل مخاطرة.
